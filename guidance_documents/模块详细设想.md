A.1 注解层

● com.litescheduler.core.annotation.ScheduledTask
方法 / 内容
● 注解字段：String name() default "", String cron(), boolean async() default true, String group() default "default", String description() default ""
实现步骤
1. 新建注解类，使用 @Target(ElementType.METHOD) 和 @Retention(RetentionPolicy.RUNTIME)。
2. 在文档注释写清楚支持的方法签名（无参或单参数 TaskContext）。
3. 写单元测试：在测试类上用一个示例方法标注，确保反射能读到注解。
示例代码
package com.litescheduler.core.annotation;

import java.lang.annotation.*;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface ScheduledTask {
    String name() default "";
    String cron();
    boolean async() default true;
    String group() default "default";
    String description() default "";
}
为什么这样设计
● 注解提供声明式用法，使用门槛低；字段覆盖了管理面板需要的元数据（name/group/description）。

A.3 插件接口与管理器（包：com.litescheduler.core.plugin）
必须类 / 接口
1. TaskPlugin（接口）
  ○ 方法：default void before(TaskContext ctx), default void after(TaskContext ctx), default void onError(TaskContext ctx, Throwable e)
2. PluginManager（组件）
  ○ 字段：List<TaskPlugin> plugins
  ○ 方法：void before(TaskContext), void after(TaskContext), void onError(TaskContext, Throwable)
实现步骤
1. 实现 TaskPlugin 接口并提供默认实现方法（default），避免每个插件都实现全部方法。
2. 实现 PluginManager，通过 constructor 注入 List<TaskPlugin>，在每个方法中依序调用插件，捕获插件异常避免传播。
3. 添加 @Order 的支持：如果插件需要顺序，使用 Spring 的 @Order 注解控制注入顺序。
示例代码（PluginManager）
package com.litescheduler.core.plugin;
@Component
public class PluginManager {
  private final List<TaskPlugin> plugins;
  @Autowired
  public PluginManager(List<TaskPlugin> plugins) { this.plugins = plugins; }
  public void before(TaskContext ctx) {
    for (TaskPlugin p : plugins) {
      try { p.before(ctx); } catch(Throwable t) { /* log and ignore */ }
    }
  }
  // ... after/onError similar
}
为什么这样设计
● 插件机制解耦横切关注点（日志/通知/锁），提高扩展性：新增行为只需新增插件并注册，不改核心逻辑。

A.4 执行器（包：com.litescheduler.core.executor）
必须类 / 接口
1. TaskExecutor（接口）
  ○ 方法：void execute(TaskContext ctx)
2. SimpleTaskExecutor（组件，实现）
  ○ 字段：ExecutorService pool, PluginManager pluginManager
  ○ 行为：
    ■ 在 execute 中根据 def.isAsync() 决定同步/异步
    ■ 调用插件链（before/after/onError）
    ■ 反射调用方法（支持无参或单参数 TaskContext）
    ■ 收集时长并（异步）写入 TaskLog
实现步骤
1. 定义接口。
2. 实现 SimpleTaskExecutor：构建线程池（从配置读取线程数），实现 invokeAndHandle 流程（startTime、plugin before、invoke、plugin after、catch -> plugin onError、persist log）。
3. 为线程池设置合适拒绝策略（示例使用 CallerRunsPolicy 可避免丢任务）并监控线程池状态用于调优。
关键代码片段（执行骨架）
public void execute(TaskContext ctx) {
  if (ctx.getDefinition().isAsync()) pool.submit(() -> invokeAndHandle(ctx));
  else invokeAndHandle(ctx);
}
private void invokeAndHandle(TaskContext ctx) {
  ctx.setStartTime(Instant.now());
  pluginManager.before(ctx);
  try { invokeMethod(ctx.getDefinition()); pluginManager.after(ctx); }
  catch(Throwable e){ ctx.setError(e); pluginManager.onError(ctx,e); }
  finally { persistLogAsync(ctx); }
}
为什么这样设计
● 将“如何执行任务”与“何时触发任务”分离（单一职责），使执行器专注于安全执行、错误处理与插件回调，便于替换更复杂执行器（如远程 worker）。

A.5 调度器（包：com.litescheduler.core.scheduler）
必须类 / 接口
1. Scheduler（接口）
  ○ 方法：void schedule(TaskDefinition def), void unschedule(String taskId), void start(), void stop(), void triggerNow(TaskDefinition def)
2. ThreadPoolScheduler（实现）
  ○ 字段：ThreadPoolTaskScheduler taskScheduler, Map<String, ScheduledFuture<?>> futures, TaskExecutor executor
  ○ 行为：
    ■ schedule：若 cron 可解析为 number -> scheduleAtFixedRate(seconds)；否则使用 CronTrigger
    ■ 保存 ScheduledFuture 以便 unschedule 调用 cancel(true)
    ■ triggerNow 直接调用 executor.execute(new TaskContext(def))
    ■ stop cancels all futures and shutdown scheduler
3. （可选）QuartzScheduler（实现）— 映射到 Quartz job/trigger
实现步骤
1. 先实现 ThreadPoolScheduler：使用 Spring 的 ThreadPoolTaskScheduler 初始化线程池并 initialize()。
2. schedule：尝试解析 def.getCron() 为数字秒；若非数字，用 new CronTrigger(def.getCron())。
3. unschedule：从 futures map 取出并 cancel(true)。
4. triggerNow：直接构造 TaskContext 并交给 executor 执行（不修改 futures map）。
5. 编写单元测试验证 schedule -> executor 被调用、unschedule 能取消 future、triggerNow 即时执行。
示例代码（schedule + unschedule）
ScheduledFuture<?> future = taskScheduler.schedule(runnable, new CronTrigger(def.getCron()));
futures.put(def.getId(), future);
...
public void unschedule(String id) {
  ScheduledFuture<?> f = futures.remove(id);
  if (f != null) f.cancel(true);
}
为什么这样设计
● 使用 Spring ThreadPoolTaskScheduler 简化 cron 支持，保存 ScheduledFuture 以实现任务生存期控制；并提供 triggerNow 支持单次即时触发，方便管理控制台使用。

A.6 注册器与注册表（包：com.litescheduler.core.registry）
必须类
1. TaskRegistry
  ○ 字段：Map<String, TaskDefinition> map
  ○ 方法：
    ■ void register(TaskDefinition def)
    ■ TaskDefinition get(String id)
    ■ Collection<TaskDefinition> getAll()
    ■ void unregister(String id)
    ■ void enable(String id), void disable(String id)
2. TaskRegistrar（组件）
  ○ 行为：
    ■ 在 ContextRefreshedEvent 时扫描 Spring 容器 beans
    ■ 对每个 bean 使用 AopUtils.getTargetClass(bean) 找到原始类
    ■ 遍历方法查找 @ScheduledTask 注解，构造 TaskDefinition 并调用 registry.register(def) 和 scheduler.schedule(def)
实现步骤
1. 实现 TaskRegistry 使用 ConcurrentHashMap。
2. 实现 TaskRegistrar：遍历 applicationContext.getBeanDefinitionNames(), 取得 bean, targetClass, method, 注解。
3. 处理代理问题：使用 AopUtils.getTargetClass(bean) 与 targetClass.getMethod(...)。
4. 校验方法签名并记录日志（成功/失败扫描）。
5. 单元测试：创建带注解的 bean（模拟代理），启动 Spring Test Context，断言 registry 有正确条目且 scheduler 正确被调用（使用 Mock Scheduler）。
为什么这样设计
● 自动发现与注册降低使用门槛，使用户只需注解方法即可；Registry 提供程序化管理接口支持 REST/控制台集成。

B.2 RetryPlugin
类
● com.litescheduler.plugins.RetryPlugin implements TaskPlugin
方法
● onError(TaskContext, Throwable): 检查并重试（基于计数 _retry_count 存在 ctx.attributes）
实现步骤
1. 用配置 maxRetries、backoffMs。
2. 在 onError 读取计数并如果未超过则提交一个重试任务到 executor（不要在 onError 中 Thread.sleep 阻塞）。例如：executorService.schedule(() -> executor.execute(ctx), backoffMs, TimeUnit.MILLISECONDS)。
3. 测试：构造一个会失败的 task，验证重试次数与最终成功/失败转换。
为什么
● 重试是任务执行稳定性的重要策略，插件实现避免将逻辑耦合到执行器里。

B.3 RedisLockPlugin
类
● com.litescheduler.plugins.RedisLockPlugin implements TaskPlugin
方法
● before: 使用 Redis SETNX 获取锁（带过期），失败时抛出 IllegalStateException 或按配置 skip
● after / onError: 释放锁（建议用 token 与 Lua 脚本安全释放）
实现步骤
1. 注入 StringRedisTemplate（required=false），如果 null 则 no-op。
2. 用 opsForValue().setIfAbsent(key, token, Duration) 获取锁，保存 key/token 到 ctx.attributes。
3. 释放时比对 token 再删除（生产应用使用 Lua 脚本保证原子）。
4. 测试：在两个并发实例模拟获取锁，一个会失败验证策略；也测试释放逻辑。
为什么
● 在集群环境中，避免重复执行是必须考虑的；做成插件可选且可在无 Redis 时回退。

每个模块设计理由（汇总）
● core：把框架的最小接口与职责放在此处，便于替换与测试；不强依赖 Spring 保持可移植性。
● plugins：把横切关注点做成插件，增强可扩展性，业务系统只需增加组件即可。
● starter：对接 Spring Boot 生态，降低用户引入与配置复杂度，符合企业常见做法（Starter 模式）。
● samples：演示与测试必需模块，能在答辩中直接跑起来并演示功能。
● storage（可选）：生产级调度需要持久化，能加入可靠性与运维特性，丰富论文内容。
● security/ops（可选）：运维控制与审计是企业级加分项。
