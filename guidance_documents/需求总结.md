Lite-Scheduler 是一个 轻量级、可扩展、无侵入、可插拔 的 Java 定时任务框架，设计目标是比 Quartz 更简单，比 Spring Scheduler 更灵活，比 XXL-Job 更轻量，适合作为一个课程毕设、开源小项目，也能实际落地使用。
下面是完整的需求总结👇

1. 📌 系统整体需求（Core Vision）
   Lite-Scheduler 需要提供一个 可独立运行 / 可作为 Starter 引入的通用调度组件，满足：
   ● 无需外部依赖（可选接入 Redis、数据库等扩展功能）
   ● 开发者只需写一个 @ScheduledTask 注解的方法即可运行
   ● 自动扫描、注册、管理所有任务
   ● 可扩展，可插拔
   ● 支持日常常见的调度模式
   ● 支持运行状态监控（日志 + 执行上下文）
   ● 适合作为一个中型项目的框架级组件
   一句话总结系统目标：
   “用最少的代码，实现一个可运行、可扩展、可插拔、易理解的 Java 任务调度框架。”

2. 📌 功能需求（Functional Requirements）
   以下是项目必须提供的功能（按优先级排列）。

2.1 核心调度功能（必须）
✓ R1 —— 支持基于注解的任务定义
● 使用 @ScheduledTask(cron = "...", name = "...") 提供任务元信息
● 扫描所有任务方法，转换为 TaskDefinition
● 自动注册到 TaskRegistry
➡ 作用： 极简 API，让用户上手成本最低。

✓ R2 —— 支持 cron/固定速率调度
框架需要实现两种最基础的调度模式：
1. Cron 调度（支持简单表达式，如 */5 * * * * *）
2. 固定频率（fixedRate / fixedDelay）
   由 ThreadPoolScheduler 统一调度。

✓ R3 —— 可手动触发任务执行
提供：
● triggerNow(taskName)
● unschedule(taskName)
● reschedule(taskName, newCron)
➡ 为了管理端（或者未来控制面板）预留能力。

✓ R4 —— 任务执行器（TaskExecutor）管理任务生命周期
必须管理以下事件：
● executeBefore
● execute
● executeAfter
● handleException
并收集任务执行上下文 TaskContext。
➡ 这是实现插件机制的基础。

✓ R5 —— 任务执行上下文（TaskContext）与执行日志
每次执行需要包含：
● 任务名称
● 开始时间、结束时间
● 耗时
● 执行状态（成功/失败）
● 异常堆栈（如有）
➡ 提供透明可观测性，便于扩展 UI、持久化等。

2.2 插件扩展功能（可选但推荐）
框架必须提供：
✓ R6 —— 插件机制（PluginInterceptor）
每个插件都可以拦截执行流程：
beforeExecute(ctx)
afterExecute(ctx)
onException(ctx, e)
supports(taskDefinition)
框架必须内置至少 3 个插件：
内置插件：
1. LoggerPlugin：打印任务执行日志
2. RetryPlugin：失败自动重试（基于注解）
3. RedisLockPlugin：分布式任务锁（可选）
   ➡ 这个模块是你毕设亮点，用于展示“可扩展性”。

2.3 框架自动配置（Starter）
✓ R7 —— Spring Boot 自动配置
包含：
● 任务扫描器（TaskScanner）
● 注册器（TaskRegistrar）
● 调度器（ThreadPoolScheduler）
➡ 确保用户只需引入 starter 即可使用。

2.4 插件解耦与可选依赖机制
✓ R8 —— Redis 插件自动装配（Optional Dependency）
如果用户项目有 Redis 依赖 → 自动启用
如果没有 → 自动关闭
➡ 展示优秀的可插拔设计。

3. 📌 非功能需求（NFR）
   非功能需求是论文和框架评价的重要部分。

✓ NFR1 —— 轻量
● 核心模块不超过 20 个类
● 不依赖 Quartz / XXL-Job / ElasticJob

✓ NFR2 —— 可扩展
提供完整 SPI 模型（插件机制），便于第三方扩展。

✓ NFR3 —— 易理解
整个框架代码目标在 2000 行以内。

✓ NFR4 —— 稳定
线程池必须隔离、可配置。
调度取消、重调度必须有管理能力。

✓ NFR5 —— 可展示（适合作为毕业设计答辩）
如：
● 生命周期图
● 类图（PlantUML）
● 执行流程图
● 示例代码
● 扩展点示例
● 插件示例
这些都会大大提升可视化效果。

4. 📌 系统模块需求（总体结构）
   Lite-Scheduler 项目结构：
   lite-scheduler-core       （核心调度与任务执行）
   lite-scheduler-plugin     （插件系统与内置插件）
   lite-scheduler-spring     （Spring Boot 启动器）
   lite-scheduler-example    （示例应用）

5. 📌 各模块需求概述（重点）
   我会简要列一下，每个模块做什么、为什么要这么拆：

5.1 lite-scheduler-core（核心模块）
目标
提供最小可运行调度框架。
必须包含：
● TaskDefinition（任务元数据）
● TaskContext（一次执行上下文）
● TaskRegistry（任务注册表）
● TaskExecutor（任务执行器）
● ThreadPoolScheduler（调度器）
● TaskSchedulerManager（统一管理调度状态）
为什么这样分？
核心模块要确保：
● 不依赖 Spring
● 可被任何框架复用
● 保持最小、纯粹

5.2 lite-scheduler-plugin（插件模块）
目标
提供增强能力与拦截机制。
必须包含：
● PluginInterceptor 接口
● PluginManager
● LoggerPlugin
● RetryPlugin
● RedisLockPlugin（optional）
为什么单独拆？
● 方便未来用户自定义 plugin
● 不污染核心逻辑
● 便于论文强调：框架可扩展性

5.3 lite-scheduler-spring（Starter 自动配置）
目标
让用户仅需写一个 @ScheduledTask 即可。
包含：
● 注解 @ScheduledTask
● TaskScanner（扫描注解）
● TaskRegistrar（注册所有任务）
● AutoConfiguration（自动配置）
为什么拆出来？
● Spring Boot Starter 属于一个独立形式
● 论文能说明“扩展能力”
● 用户看到时体验最佳

5.4 lite-scheduler-example（示例应用）
必须包含：
● DemoTask 示例任务
● application.yml 配置示例
● 演示插件运行日志
这是你实践的 playground。

6. 📌 Lite-Scheduler 的最终价值总结（适合写在论文里）
   Lite-Scheduler 的系统价值：
1. 轻量性： 无需数据库、无需外部服务即可运行
2. 无侵入性： 任务只需要一个注解即可加入调度
3. 可扩展性： 插件机制赋予高度可定制能力
4. 可插拔性： Redis 插件、重试插件按需启用
5. 可观测性： 提供完整执行上下文与日志
6. 可管理性： 提供任务启动/停止/手动触发能力
7. 适合毕设： 复杂度中等，具有框架化特色
8. 可生产可用： 真正可以在业务中跑起来
9. 模块化结构清晰
10. 极强演示效果（答辩时加分）
